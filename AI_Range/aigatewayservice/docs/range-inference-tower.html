AI-Range · Implementation Reference

Range Inference Tower

Standing up a single hardened GPU tower as the shared AI service for a multi-enclave cyber range — and folding the existing aigatewayservice into it as the policy plane rather than replacing it. What survives untouched, what gets rewritten, and every integration point in between.

Target Ace LogicAD Fusion · TR PRO 9975WX · 2× RTX PRO 6000 Max-Q Base RHEL 9 / DISA STIG Runtime podman + quadlet Serving vLLM + Open WebUI

01The shape of the system

The tower carries two completely different kinds of traffic, and almost every design decision downstream follows from keeping them separated but served by one pool of weights.

Class A — student chat. Interactive, bursty, many concurrent humans, fully untrusted input (students will paste malware samples and hostile payloads into the box by design, and will try to jailbreak the model as a lab exercise). Path: browser → enclave proxy → Open WebUI → gateway → vLLM.

Class B — range automation. Programmatic, low-volume, latency-budgeted, schema-constrained. This is what aigatewayservice already does: the four engine modes, driven by the event plane and the instructor dashboard. Path: range control plane → broker → event adapter → gateway → vLLM.

The one decision that shapes everything else

Open WebUI can point straight at vLLM's OpenAI-compatible port. Do not let it. Every guardrail your project already implements — prompt versioning, schema validation, retry-then-safe-fallback, provenance stamping — lives in the gateway. A direct Open WebUI → vLLM path is an unaudited, unattributed, unmetered second door into the same GPUs, and on a training range you need to be able to answer "which student asked what, on which exercise, against which model version" for every single token generated.

So: vLLM binds to loopback only, and the gateway is the sole client. That means the gateway grows an OpenAI-compatible surface it does not have today (§8) — the largest single piece of new code in this plan.

Preserve this

The ResourceRequestRaised boundary in eventAdapter.js — the AI reasons about what infrastructure is needed and why, the control plane's Resource Scheduler is the only thing that can actually provision — is the single most important safety property in the existing design. Nothing in this plan touches it. Extend the same principle to the chat path: the student-facing model gets no tool calling that can reach the network.

02GPU allocation and storage

192 GB of VRAM across two cards, but they are not one pool. Plan around that, not against it.

No NVLink — so avoid tensor parallelism

The RTX PRO 6000 Blackwell workstation cards have no NVLink bridge; cross-GPU traffic goes over PCIe. --tensor-parallel-size 2 works but pays an all-reduce penalty on every decode step, and it couples both cards' lifecycles to one unit. Fortunately you don't need it: gpt-oss-120b in MXFP4 is roughly 61 GB of weights and fits on a single 96 GB card with room for a real KV cache. Every model in your list fits on one card. Treat the cards as two independent serving domains.

Each co-located vLLM process interprets --gpu-memory-utilization as a fraction of the whole card and pre-allocates it, so the fractions must sum below 1.0 with about 0.5–1 GB of CUDA context overhead per process left over. The active set is exactly what your brief says it should be — group_vars, not code (§11).

Why a separate LoRA host

Student-trained adapters are untrusted artifacts. Loading one into the same vLLM process that serves the rest of the class puts a student's fine-tune in the batch scheduler alongside everyone else's requests. Give them their own process with its own memory slice, and let it crash without taking the classroom down.

03Host build under the RHEL 9 STIG

Four STIG controls will break a GPU inference stack in ways that look like unrelated bugs. Solve them during the build, not during a class.

Secure Boot vs. the NVIDIA kernel module

The STIG requires UEFI Secure Boot enabled. The NVIDIA kernel modules are out-of-tree and unsigned, so they will silently fail to load and nvidia-smi will report no devices. Enroll a Machine Owner Key at build time and sign the modules, and re-sign on every kernel or driver update — this is the single most common way a hardened GPU host comes back from patching with no GPUs.

# build-time, once
openssl req -new -x509 -newkey rsa:2048 -keyout MOK.priv -outform DER \
  -out MOK.der -nodes -days 36500 -subj "/CN=AI-Range Module Signing/"
mokutil --import MOK.der          # reboot, enroll at MOK manager

# after every driver/kernel update — wire this into a dkms hook
/usr/src/kernels/$(uname -r)/scripts/sign-file sha256 MOK.priv MOK.der \
  /lib/modules/$(uname -r)/extra/nvidia*.ko

# and blacklist nouveau
echo "blacklist nouveau" > /etc/modprobe.d/blacklist-nouveau.conf

Use the NVIDIA data-center/RHEL 9 repo package rather than the .run installer so DKMS handles rebuilds. Blackwell (sm_120) needs a recent driver branch and CUDA 12.8 or later — verify nvidia-smi reports both cards and that torch.cuda.get_device_capability() returns (12, 0) before you go further.

FIPS mode breaks MD5 in Python libraries

The STIG requires FIPS 140-3 mode. Under FIPS, hashlib.md5() raises instead of returning a digest — and several parts of the HuggingFace and web-framework ecosystem call MD5 for non-security purposes like cache keys and ETags. The failure surfaces as an opaque ValueError deep in a library at container start.

# confirm mode
fips-mode-setup --check
cat /proc/sys/crypto/fips_enabled     # must be 1

Test each container image under FIPS during Phase 1. Where a dependency trips, the fix is a patched call site using hashlib.md5(data, usedforsecurity=False), which is permitted under FIPS on RHEL 9's Python. Pin the image digests once you have a working set — an unpinned base-image bump can reintroduce this at 03:00 via ansible-pull.

SELinux and GPU device access from containers

With SELinux enforcing, containers cannot open /dev/nvidia* by default. Use the Container Device Interface rather than --privileged:

setsebool -P container_use_devices 1
nvidia-ctk cdi generate --output=/etc/cdi/nvidia.yaml
nvidia-ctk cdi list                   # expect nvidia.com/gpu=0, =1, =all

Then every quadlet references AddDevice=nvidia.com/gpu=0 and stays unprivileged. Regenerate the CDI spec after driver updates — an ansible handler on the driver package is the right place. Volume mounts need :z (shared) or :Z (private) labels; the read-only model store wants :ro,z since several containers read it.

noexec on /tmp vs. Triton kernel compilation

STIG mounts /tmp with noexec. vLLM compiles Triton kernels and CUDA graphs at startup and writes them to a cache under the user's temp or home directory; if that path is noexec, startup fails or silently falls back to a slow path. Redirect every cache to the U.2 array explicitly — do not rely on defaults:

Environment=HF_HOME=/srv/airange/cache/hf
Environment=HF_HUB_OFFLINE=1
Environment=TRANSFORMERS_OFFLINE=1
Environment=VLLM_CACHE_ROOT=/srv/airange/cache/vllm
Environment=TRITON_CACHE_DIR=/srv/airange/cache/triton
Environment=TORCHINDUCTOR_CACHE_DIR=/srv/airange/cache/inductor
Environment=XDG_CACHE_HOME=/srv/airange/cache/xdg
Environment=TMPDIR=/srv/airange/cache/tmp
Environment=OUTLINES_CACHE_DIR=/srv/airange/cache/outlines
Offline by construction

HF_HUB_OFFLINE=1 is not an optimization, it's a control. The tower must never reach HuggingFace at runtime. Weights are pre-staged to /srv/airange/models through your approved artifact path, checksummed, and referenced by local path in the quadlet. Ansible verifies the checksum; it does not download the model. Publishing weights as OCI artifacts into your internal registry and pulling with oras gives you the same provenance and signing story as your container images.

Other host items

  • Rootless podman for every service account, with loginctl enable-linger <user> so units survive logout. CDI device access works rootless. Keep the podman API socket disabled.
  • No local accounts on the chat UI. The STIG's password complexity, lockout, and reuse rules are painful to satisfy in Open WebUI's local auth. Federate to the range IdP instead (§6) and turn local signup off entirely.
  • DoD consent banner on the Open WebUI login page and on SSH. Open WebUI supports custom login content; template it from Ansible so it's version-controlled.
  • Persistent journald with size caps, plus auditd watch rules on /srv/airange/models and /srv/airange/adapters so weight substitution is detectable.
  • firewalld zones bound per interface, default-deny egress. The tower needs no outbound internet at all after staging.

Two flags that matter more than they look

HealthStartPeriod=600s — loading 61 GB of weights and warming CUDA graphs takes minutes, and a default health check will kill the container mid-load in a restart loop that looks like a crash.

--disable-log-requests — vLLM otherwise writes prompts to the container log. On this box prompts are student work product subject to a retention policy; you want exactly one audit path (the gateway, §8), not a second uncontrolled copy in journald.

Making training and elective serving mutually exclusive

A LoRA training run needs ~40 GB on GPU 1, which it can't have while four serving processes hold 0.9 of the card. Let systemd enforce it rather than a human remembering:

/etc/containers/systemd/lora-train@.container (excerpt)

[Unit]
Description=LoRA fine-tune · %i
Conflicts=vllm-mistral.service vllm-devstral.service
After=vllm-mistral.service vllm-devstral.service

Starting lora-train@cohort3.service now stops the two 24 B electives and frees ~50 GB; when it exits, an OnFailure/ExecStopPost hook or a plain systemd dependency brings them back. GPU 0 — the primary chat model the whole class is using — is never touched by a training job.

05vLLM configuration

Context length is your capacity dial

KV cache is what limits concurrency, and it scales linearly with --max-model-len. Serving gpt-oss-120b at its full 128 K context means a handful of students can each consume gigabytes of cache. Cap it. For classroom chat, 16 K–32 K is generous — few student conversations exceed it, and the ones that do are usually a sign the session should be reset anyway. Make it a group_vars value so an instructor running a long-context exercise can raise it for that block.

--enable-prefix-caching is close to free money here. Every student in a cohort shares the same system prompt and, with RAG, frequently the same retrieved course chunks. Prefix caching skips re-prefilling those tokens, which is a large fraction of prefill work in a classroom.

--max-num-seqs bounds the batch. Set it deliberately: too low and the GPU idles while requests queue, too high and per-stream tokens/sec drops below reading speed and every student experiences the model as slow. Start at 32 for the primary and tune from the Phase 3 measurements.

Pin the version, in the image

vLLM moves fast and quantization kernel support for new silicon lands unevenly. Build one internal image with a pinned vLLM version, pinned PyTorch/CUDA, and your FIPS patches; push it to the internal registry by digest; reference the digest in the quadlet. An unpinned :latest plus a 30-minute ansible-pull timer is a recipe for a model that stops loading during a lab with no correlated human action to blame.

06Open WebUI, tenancy, and RAG

One instance per enclave

Open WebUI keeps conversations, users, prompts, and its RAG index in one database. Sharing a single instance across enclaves means Cloud A's students and Cloud B's students share a namespace — and shared chat history and a shared vector index across a range boundary is a data-spill vector you cannot easily argue away in an authorization package. Run three small instances instead. They're a few hundred megabytes of RAM each, and separation becomes structural rather than a matter of correct RBAC configuration.

Note that Open WebUI points at the gateway, not at vLLM, and carries a per-enclave token. That token is how the gateway knows which tenant a request belongs to before it has even looked at the user's JWT.

Turn these off and keep them off

Web search, URL-fetch RAG, code interpreter, and image generation. Students paste hostile content into this box deliberately — a model with a fetch tool plus prompt-injectable input is a request forgery primitive pointed at the inside of your range. There's no egress anyway, but disable them explicitly so a future Open WebUI upgrade defaulting one back on doesn't hand it to you.

Course-content RAG

Keep the corpus in Git alongside the Ansible repo (or an internal object store for large PDFs). Ansible syncs /srv/airange/corpus/<enclave>/, and a small ingest job re-indexes on content change into that enclave's Chroma volume. Embeddings go through the gateway to vllm-embed, so retrieval is on the same audited path as generation.

Two details worth getting right: apply nomic's search_document: prefix at ingest and search_query: at retrieval — mixing them degrades recall noticeably and silently. And treat retrieved course content as data the model reads, never as instructions: the gateway's system prompt should say so explicitly, because a student who can get a document into the corpus can otherwise steer everyone's assistant.

Identity mapping

The OIDC sub claim becomes student_id, and a group or custom claim carries cohort and exercise enrollment. This is what makes per-student attribution, per-student quota, and the transcript retention policy possible — and it's the same identifier the range's event plane already uses in StateSnapshotUpdated, which lets you join a student's chat history to their exercise telemetry in the after-action report.

Existing gap worth closing now

eventAdapter.js publishes recommendations with approval_status: "pending_approval", and nothing in the repo consumes them. There is no endpoint to list the queue and no UI to approve or reject. In a live classroom that queue is where instructors spend their attention — and the rejection data is what the after-action report's "call out rejected recommendations" rule depends on. Add GET /v1/approvals, POST /v1/approvals/:id/{approve,reject}, a persisted queue, and a dashboard panel.

Health checks have to mean something

GET /v1/health currently returns {status: "ok"} unconditionally. Once vLLM is downstream, that's actively harmful — nginx and Open WebUI will keep routing to a gateway whose models are all still loading. Split it: /v1/health stays a trivial liveness probe, and a new /v1/ready polls each upstream's /health and reports per-model readiness. Open WebUI's model list should be built from ready upstreams only, so students never see a model they can't actually use.

Housekeeping

The repo has no commits yet and .env exists on disk with .gitignore covering it — good, keep it that way. Before this goes to GitLab: initialize with signed commits, confirm .env was never staged, and move every real secret to ansible-vault delivered as a systemd EnvironmentFile (§11).

08The chat proxy

One new module carries the student-facing path. It looks like a pass-through and is mostly a policy engine.

Request pipeline

  1. Authenticate — verify the enclave token, then the student's OIDC JWT. Resolve { tenant, student_id, cohort, role }.
  2. Authorize the model — is the requested model on this tenant's allowlist and currently ready? Reject with a message a student can act on, not a 502.
  3. Check quota — per-student tokens/hour and concurrent-stream cap. Refusing here is far better than letting one student starve the batch scheduler.
  4. Clamp parameters — cap max_tokens, clamp temperature, reject n > 1, strip any tools the student's role isn't allowed to use.
  5. Inject the range system prompt — versioned, same discipline as the four existing mode prompts. Establishes scope, states that retrieved documents are data and not instructions, and carries the training-context framing.
  6. Forward to the mapped upstream, streaming.
  7. Tee the stream — relay SSE chunks to the client while assembling the full response for the audit record.
  8. Record — on stream end (or abort), write the audit row with token counts, latency, finish reason, and prompt version.
The one genuinely tricky part

Streaming. You must pipe the upstream SSE body straight through without buffering — a student watching a paused cursor for eight seconds while you accumulate the whole response is the difference between "fast" and "broken" — while still assembling the text for audit. In Node, pipe the response body and accumulate in a transform. Handle client disconnect by aborting the upstream request (AbortController), or an abandoned tab holds a KV-cache slot for the full generation. Test aborts explicitly; it's the most common bug in hand-rolled LLM proxies.

Surface

RouteBehavior
GET /v1/modelsReady upstreams filtered by the caller's tenant allowlist. Open WebUI populates its model picker from this.

Note the path collision: your existing REST API is already mounted at /v1 with /v1/recommendations and friends. OpenAI clients expect /v1/chat/completions specifically, so they can coexist — but it's cleaner to mount the range API at /v1/range/* and reserve /v1/* for the OpenAI-compatible surface. That's a breaking change to the dashboard and OpenAPI spec, which is cheap now and expensive after three clouds are integrated. Decide before Phase 3.

Should you just use LiteLLM instead?

Reasonable question — it gives you routing, key management, and budgets out of the box. The argument against: none of it knows what an exercise, a cohort, or an enclave is, and your audit requirement is to join inference records to range telemetry by exercise_id and student_id. You'd end up writing the range-aware layer anyway, and then running two proxies. Since the gateway already exists and already owns the audit vocabulary, extend it. Revisit if you later need multi-provider failover to something off-box.

09Structured output on vLLM

This is where the existing design gets a real upgrade rather than a port.

Today each mode calls the model, validates with ajv, retries once on failure, then falls back. vLLM supports guided decoding — constraining generation at the token level against a JSON Schema, so malformed output is structurally impossible rather than merely detected. Feed it the very same schema objects in src/schemas/:

async function callRecommendationModel({ systemPrompt, userPrompt, tier, priorError }) {
  const res = await fetch(`${tier.baseUrl}/v1/chat/completions`, {
    method: "POST",
    headers: { "content-type": "application/json" },
    signal: AbortSignal.timeout(tier.timeoutMs),
    body: JSON.stringify({
      model: tier.model,
      temperature: tier.temperature,
      max_tokens: 512,
      messages: [
        { role: "system", content: systemPrompt },
        { role: "user", content: priorError
            ? `${userPrompt}\n\nPrevious attempt was invalid: ${priorError}`
            : userPrompt },
      ],
      // same object ajv validates against — one source of truth
      response_format: {
        type: "json_schema",
        json_schema: { name: "recommend_intervention",
                       schema: guidedRecommendationSchema, strict: true },
      },
    }),
  });
  if (!res.ok) throw new Error(`vllm ${res.status}: ${await res.text()}`);
  const body = await res.json();
  return JSON.parse(body.choices[0].message.content);
}

Keep the ajv validation and the fallback anyway. Guided decoding guarantees the shape, not the semantics — the model can still emit a well-formed recommendation with a target_id that doesn't exist in the scenario graph, which is precisely what targetExistsInScenario() already catches. Belt and braces, and the fallback path stops being the common case.

Your recommendation schema needs restructuring first

recommendation-output uses JSON Schema if/then/else to require target_id for every type except no_action. Grammar backends implement a subset of JSON Schema and conditional keywords are generally not in it — the schema will likely be rejected or silently ignored at compile time. Restructure the guided variant as a oneOf of two concrete branches (a no_action object and a with-target_id object), keep the current if/then/else schema for ajv validation, and assert in a unit test that any object valid under one is valid under the other. Verify against your pinned vLLM build early — this is a Phase 3 blocker if it's discovered late.

Two smaller notes. Guided decoding costs a grammar compile on first use per schema; it's cached, so warm the four schemas at gateway startup rather than paying it inside a student-visible request. And the report path stays unconstrained — it's narrative output, correctly so.

10The adaptation lab

Your stated core mission requirement — students adapting models — is the part of this build that most benefits from owning the hardware, and vLLM has a feature that makes the loop genuinely tight.

vLLM can load and unload LoRA adapters at runtime against an already-resident base model. With --enable-lora and VLLM_ALLOW_RUNTIME_LORA_UPDATING=1, a student's adapter becomes a servable model in seconds, without a restart and without a second copy of the 8 B base in VRAM. That turns "fine-tune a model" from a batch job into a lab a student can iterate on inside one session:

  1. Student prepares a dataset in the enclave and submits a training run.
  2. lora-train@<run-id> starts, systemd stops the 24 B electives (§4), training gets ~50 GB on GPU 1.
  3. Adapter lands in /srv/airange/adapters/<cohort>/<student>/<run-id>/.
  4. Instructor (or an automated hook) loads it into vllm-lora via the gateway's admin route.
  5. It appears in that enclave's model picker, scoped to that student or cohort, and they chat with what they built.
  6. Electives restart when the run finishes.

Granite 3.3 8B is the right base — LoRA on an 8 B model at modest sequence length fits comfortably in the freed budget and trains fast enough for a class period. Your OLMo 2 7B alternate is a genuinely good call for courses that examine training data provenance, and it drops into the same slot without changing anything structural.

Guardrails

  • Per-student disk quota on the adapter tree. Checkpoints are large and students will forget to clean up.
  • Adapters are untrusted. Serve them only from the isolated vllm-lora process, scoped so a student's adapter is visible to that student, their cohort, and instructors — never range-wide by default.
  • Bound the queue. Only one training run at a time on GPU 1, with a scheduled window. Twelve students each submitting a job in the last ten minutes of class is the predictable failure mode.
  • Audit the adapter load the same as any other inference config change — who loaded which adapter, when, from which run.
  • Cap --max-lora-rank to bound per-adapter memory, and --max-loras to bound how many are resident at once.

11GitOps convergence

ansible-pull on a 30-minute timer is the right pattern for one hardened box with no inbound management path. Three things about it need explicit design or it will cause outages.

Problem one: converge must not restart the models

A naive handler chain means any change touching a vLLM template restarts a container that takes minutes to reload 61 GB of weights and drops every in-flight student stream. On a 30-minute timer that is a recurring, unattended, mid-class outage.

Gate it. Disruptive changes require an explicit flag, so the default converge is always safe:

# group_vars/tower.yml
ai_range_allow_disruptive: false     # flipped in a merge request for a window

# roles/vllm/handlers/main.yml
- name: restart vllm units
  ansible.builtin.systemd:
    name: "{{ item }}"
    state: restarted
    daemon_reload: true
  loop: "{{ vllm_units }}"
  when: ai_range_allow_disruptive | bool

- name: warn that a restart is pending
  ansible.builtin.debug:
    msg: "Unit files changed; restart deferred. Set ai_range_allow_disruptive."
  when: not (ai_range_allow_disruptive | bool)

Write a marker file when a restart is deferred and expose it through node_exporter's textfile collector, so "tower has pending changes" is a dashboard state rather than tribal knowledge. Everything non-disruptive — nginx config, gateway env, corpus sync, quota tables, allowlists — converges freely every 30 minutes.

Problem two: what the tower actually tracks

Pointing ansible-pull at main means any merged commit reaches production within 30 minutes. Point it at a deploy branch that only advances by an explicit, reviewed fast-forward. Engineers commit to main freely; promotion to the tower is a separate, deliberate act.

[Unit]
Description=Converge AI-Range tower from GitLab

[Service]
Type=oneshot
ExecStart=/usr/bin/ansible-pull \
  -U https://gitlab.internal.range/ai-range/tower.git \
  -C deploy \
  --accept-host-key \
  -i localhost, \
  --vault-password-file /etc/ansible/.vault-pass \
  site.yml
ExecStartPost=/usr/local/bin/write-converge-status.sh $EXIT_STATUS
Secrets

The deploy token is read-only, which protects the repo — it does nothing for what's in the repo. API keys, DB passwords, and the Open WebUI OIDC client secret go in ansible-vault. The vault password file itself is the one thing that cannot come from Git: provision /etc/ansible/.vault-pass (root, 0400) during kickstart or first boot. Ansible templates them into systemd EnvironmentFiles at 0400, and no secret ever lands in a quadlet file, a container image, or podman inspect.

Problem three: silent convergence failure

A failed or half-completed run leaves the box in an undefined state with nobody watching. ExecStartPost writes a status file with exit code and timestamp; node_exporter scrapes it; alert on "last successful converge older than 90 minutes" — three missed cycles. Add OnFailure= on the timer unit to a notification path that works without internet.

12HWIL and multi-tenancy

One physical box serving several enterprise clouds means tenant isolation is a property of the design, not of a config field.

Network

Bring each enclave in on its own tagged VLAN sub-interface with its own IP, its own firewalld zone, and its own nginx server block and TLS certificate. Default-deny everywhere; the only permitted inbound is 443 per enclave interface plus the control-plane path. No egress. Students never address the tower directly — they reach the nginx vhost on their enclave's network, and nothing else on the box is routable from a student network.

Have each enclave's ingress present a client certificate, or terminate an mTLS tunnel from the range broker. Combined with the per-enclave Open WebUI token (§6), the gateway can then establish tenancy from three independent signals before it looks at the user's JWT.

The isolation ledger

ResourceIsolationRationale
Chat historyPer enclaveSeparate Open WebUI instance and database. Never shared.
RAG indexPer enclaveSeparate Chroma volume. Course content may itself be enclave-specific.
Model weightsShared, read-onlyImmutable, checksummed, no tenant data. Safe to share.

Decide this before the ATO conversation, not during it

Enclaves sharing one vLLM process share a KV cache and a batch scheduler. There is no known cross-request data path, but prefix caching does mean timing is data-dependent across tenants, and "different clouds' students share a CUDA context" is a question an assessor will ask. If any enclave sits at a different classification or handles data the others must not see, the answer is not a config flag — it's separate vLLM processes per classification domain, which is affordable on GPU 1 and is why the primary chat model gets a dedicated card. Establish the classification model first; the VRAM plan follows from it.

Retention

Every student prompt is a training record. Decide now, encode in Ansible: how long transcripts live, who can read them, whether they are exported into the after-action report, and what happens at cohort close-out. Wire the answer into a systemd timer that prunes /srv/airange/transcripts on the policy, so retention is enforced by the machine rather than by intention.

13Observability and acceptance tests

Your table's projected numbers become measured numbers here. Design the measurement before Phase 3 so the acceptance criteria are falsifiable.

Scrape targets

  • vLLM /metrics per instance — time-to-first-token, time-per-output-token, running vs. waiting requests, KV cache utilization, preemption count. Preemptions and KV utilization are the two that predict a bad class: they tell you the batch is oversubscribed before students report slowness.
  • DCGM exporter — per-GPU utilization, memory, temperature, power. The Max-Q cards are power-limited by design; watch for sustained clock throttling under classroom load.
  • Gateway metrics — requests by tenant/model/mode, schema-validation failure rate, fallback rate, quota rejections, upstream error rate.
  • node_exporter plus the converge-status textfile (§11).

Two gateway metrics deserve alerts of their own. Schema fallback rate — if recommendIntervention starts falling back to no_action, live adaptation has silently stopped working and every exercise still looks healthy. Prompt-version drift — if the deployed prompt version doesn't match what the audit records expect, someone changed a prompt without bumping its version, and the provenance guarantee your design is built on is broken.
