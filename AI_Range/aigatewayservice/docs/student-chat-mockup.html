What students actually see: Open WebUI, configured

This isn't a custom-built app — it's Open WebUI, the chat front end already named in the original spec, pointed at the gateway's /v1/chat/completions instead of at vLLM directly. The work is configuration and restriction, not a new codebase: which models show up, which tools are switched off, what the login and consent flow look like, and what quota/branding wraps around it.

What's AI-Range-specific

1

Consent banner

Templated from Ansible per enclave, shown before the chat loads — generic monitored-system language, not a stock Open WebUI screen.

2

Model picker

GET /v1/models — only lists models this tenant is allowed to use and that just passed their health check. A model can be configured but still not appear if it isn't ready.

3

Web search / image generation

Disabled at the Open WebUI config level (ENABLE_WEB_SEARCH=false, etc.) — the tower has no outbound internet anyway, but this keeps the option from even appearing.

4

Course Content toggle

RAG retrieval through /v1/embeddings, scoped to this enclave's own indexed course material — never the open web.

5

Quota indicator

Reflects the student's rolling-hour token budget (src/quota.js). Past the limit, the request is rejected before it ever reaches a model.

6

Identity badge

Comes from the student's SSO login to Open WebUI itself, then forwarded to the gateway as X-OpenWebUI-User-* headers on every message — what makes per-student audit and quota possible.

7

System prompt (invisible)

Every message gets the fixed range system prompt prepended server-side. A student's own "ignore previous instructions" never reaches the model as a system message.
